# Android device test cases

Prepared October 20, 2026 for the current local reliability/UI pass. Cases begin as **Not run**. See [Samsung A56 device feedback](ANDROID_SAMSUNG_A56_RESULTS.md) for reported results. Existing browser and automated checks are supporting evidence, not substitutes for these device results.

## Before testing

1. Use synthetic data such as `QA Baby`, `QA checkup` and `QA supplies`. Use a disposable installation/profile/device for fresh-install, deletion and upgrade cases. Do not uninstall or clear an installation containing real records without a proven backup; Riah has no in-app backup/restore yet.
2. Install a build from this checkout. Record phone model, Android version, app version/build label, install date, build type and source revision **plus whether it includes uncommitted changes**. A Git SHA alone does not identify the current modified source.
3. Prefer Riah's development client for initial debugging and a standalone preview/release-like APK for final offline/background checks. Expo Go/browser results alone cannot close native release gates. A development client can require Metro; inability to fetch its JavaScript offline is not proof that SQLite lost records.
4. Set automatic date/time and the intended time zone. Record battery restrictions and notification permission. Start with Do Not Disturb off and notifications allowed for delivery tests; test denial separately.
5. Keep a stopwatch and copy the [results template](ANDROID_TEST_RESULTS_TEMPLATE.md). Note the current counts/volumes before each case; expected totals below are **increases from that baseline**, unless a case explicitly requires empty data.

If you need to build locally, follow the [development guide](../DEVELOPMENT.md). With the SDK/JDK ready and a USB-debugging-authorized phone:

```sh
npm ci
npm run check
npm run android -- --device
```

The existing `android` script runs Expo's local native build. It generates native files, installs the client and starts Metro; it does not deploy to a store. See [Expo's local development guide](https://docs.expo.dev/guides/local-app-development/) and [development client workflow](https://docs.expo.dev/develop/development-builds/use-development-builds/).

## Start here: first device session

Run **A01, A02, A04, A05, A06, N01, N02, D01, F01, S01, S04, I03, I04, P02, R01 and R02** first. P02 depends on creating the appointment in P01. I03/I04 need an item from I02. Start R02 early and check other screens while waiting for its notification.

Priorities: **P0** = possible data loss, crash or duplicate/corrupt records; **P1** = core behavior; **P2** = presentation, accessibility or extended checks. A reproducible P0 failure blocks release. A blocked/not-run case is not a pass. Capture usability concerns even when the underlying record saves successfully.

## Notifications on the physical phone

These checks require a native build and actual device permission. Keep the app below its current 48-schedule limit. Notification display/sound can be affected by Android/OEM settings; capture those settings and delivery times instead of silently classifying a missing alert as pass.

### Fast setup for R02

Choose the next selectable appointment time **65–80 minutes in the future**. Riah schedules the same-day reminder **one hour before**, so it should be due in roughly **5–20 minutes**. Example: at 13:07, an appointment at 14:15 makes the reminder due at 13:15. Use the phone's actual local date/time; do not change its clock to accelerate the test. Calculate the expected time after confirming the saved appointment. Android supports individual minutes; the web/iOS custom picker uses quarter-hour choices.

## Record failures so they are fixable

For each failed case capture:

- Case ID and exact steps from the last known good state.
- Expected versus actual result; whether it happens every time or intermittently.
- Phone/Android/build type/build label/source revision and dirty-tree state.
- Permission, battery/DND/network state when relevant; local time zone and due/actual times for reminders.
- A redacted screenshot or short recording, plus relevant error text. Include only a narrow redacted log excerpt if available; never upload a real care database or whole device logs to a public issue.

Use [the result template](ANDROID_TEST_RESULTS_TEMPLATE.md). Fill **Not run** for unexecuted tests and **Blocked** for missing APK/signature/tooling/time-window access. Mark a defect fixed only after its original case and nearby regression cases pass again.

## Engineering-only checks

Failed SQL writes, corrupted storage, rollback behavior and legacy cleanup flags need controlled fixtures/injection. Do not fill your phone's storage, corrupt its database, reset real app data or manipulate its clock to simulate these failures. Existing automated tests cover several such paths; physical migration/failure acceptance remains separate.

## Known limitations to keep separate from new regressions

- Recent log views show at most 15 entries; full-history browsing is pending, while complete daily totals must still be correct.
- No cloud backup, restore, partner sharing, growth tracker, weekly report or widget is implemented.
- Only the nearest 48 reminder schedules are retained; reopening reconciles future schedules. Delivery, quiet hours and lock-screen policy still need release decisions/QA.
- Simultaneous left/right feeding-timer semantics and large-text/TalkBack coverage remain to be finalized.
- Existing dependency security findings remain a release gate. A passing device run does not clear them.
